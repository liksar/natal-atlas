# Натальные карты: полное ТЗ для Codex и инструкции по развёртыванию

Дата: 5 ноября 2026. Версия: 1.1. Сценарий: создание и управление только администратором.

## 1. Задание для Codex

Разработай законченный веб-сервис построения и хранения натальных карт. Администратор добавляет клиента, вводит его данные рождения, создаёт красивую интерактивную карту и вручную отправляет клиенту постоянную персональную ссылку. Клиент только просматривает готовую карту. Владелец сервиса через защищённую админку исправляет данные клиента; после успешного перерасчёта по прежней ссылке открывается обновлённая карта.

Реализуй приложение, расчёты, админку, базу данных, оформление, тесты, контейнеры, миграции, резервное копирование, документацию и проверку восстановления. Не останавливайся на макете или статической демонстрации. Отдельно перечисли любые невыполненные пункты. Не выдавай синтетические расчёты за настоящие.

### Зафиксированные границы

- Никаких внешних API в пользовательском сценарии: расчёты, географический поиск, часовые пояса, тексты, шрифты и визуальные эффекты работают локально.
- Никакого реверс-инжиниринга и копирования ZET, его интерфейса, текстов или файлов. Swiss Ephemeris используется напрямую.
- У клиентов нет аккаунтов, входа по email, регистрации и форм ввода данных. Email и телефон не запрашиваются. Создание клиентов и карт доступно только авторизованному администратору.
- Нет PDF, платёжной системы, подписок, транзитов, совместимости, ректификации и AI-генерации в первой версии.
- Администратор входит по логину и паролю. Сброс пароля выполняется серверной CLI-командой, без почты.
- Постоянство ссылки обеспечивается базой, доменом и резервными копиями. Не обещать бессрочную доступность вне срока эксплуатации сервиса.
- Публичный интерфейс и админка на русском, тексты вынесены в словарь для последующего перевода.

Установка пакетов, начальная загрузка географических справочников, обновления и получение TLS-сертификатов могут требовать интернета. Запрет внешних API относится к рабочим сценариям сервиса, а не к установке и эксплуатации хостинга.

## 2. Технологии и архитектура

Предлагаемый обязательный стек: Python 3.12, Django 5.2 LTS с актуальными исправлениями безопасности на момент реализации, PostgreSQL 16, Gunicorn, Caddy 2, HTML-шаблоны Django, TypeScript и Vite для интерактивной SVG-карты. Точные версии библиотек закрепить lock-файлами после проверки совместимости. Если выбранная версия потеряла поддержку, применить поддерживаемую LTS и документировать замену.

Использовать штатную Django Admin с аккуратной локальной темой и отдельным сервисом редактирования/перерасчёта. Django Admin не должен напрямую сохранять поля карты в обход бизнес-логики. Публичный фронтенд и backend одного происхождения. React, Redis и Celery для первой версии не нужны.

Один Linux-сервер: Caddy завершает HTTPS и обслуживает собранную статику, Gunicorn запускает Django, PostgreSQL хранит данные. Расчёты выполняются синхронно. Контейнеры должны собираться на amd64 и arm64. Swiss Ephemeris и её Python-обвязка должны быть явно проверены на обеих архитектурах.

Из-за состояния Swiss Ephemeris внутри процесса использовать Gunicorn sync workers с одним потоком на worker. Все настройки расчёта задавать явно перед вызовами, не полагаться на состояние предыдущего запроса. Запретить threaded/async-доступ к общему состоянию библиотеки без отдельного безопасного решения.

## 3. Пользовательские страницы

### 3.1. Публичная главная

На главной нет формы создания карты, поиска клиентов или доступа к чужим картам. Показать короткую оформленную страницу сервиса с сообщением «Ваша персональная карта доступна по ссылке, которую вам отправил специалист». Данные рождения вводятся исключительно в защищённой админке. Форму добавления клиента описывает раздел 6.

### 3.2. Страница карты

Показать имя, исходные данные, выбранное место, часовой пояс и UTC-смещение на момент рождения, режим точности, карту и таблицы. Имя не включать в заголовок вкладки и метаданные предварительного просмотра.

Разделы: интерактивная карта; планеты в знаках и домах; ASC и MC при известном времени; основные аспекты; краткие текстовые пояснения. При выборе планеты подсвечиваются её положение, аспекты и соответствующая строка таблицы. Нажатие открывает пояснение; наведение не должно быть единственным способом взаимодействия.

Клиент не может редактировать карту по персональной ссылке. Вместо неработающей формы поддержки дать нейтральный текст «Если данные нужно исправить, обратитесь к владельцу сервиса». Контакт показывать только если он задан в настройках.

При неизвестном времени использовать 12:00 местного времени только как явно обозначенное условное время для планет. Не рассчитывать/не показывать ASC, MC, дома и положения планет по домам. Пометить Луну и другие чувствительные к времени показатели как приблизительные; в первой версии не показывать аспекты Луны в этом режиме. Не описывать условное время как фактическое.

Страница доступна без аутентификации по секретному token. Нет публичного каталога карт, sitemap карт или последовательных ID.

## 4. Дизайн: красивый, загадочный и астрологический

Это ключевое требование продукта. Страница должна восприниматься как дорогой персональный астрологический атлас и вызывать желание сохранить ссылку и вернуться. Дизайн рассчитан на людей, которым близки астрология, символы, космос и ощущение персонального открытия.

Направление: глубокий ночной синий/индиго, мягкие фиолетовые туманности, тёплое матовое золото, тонкие орбиты и гравированные знаки зодиака. Светлые хорошо читаемые тексты, изящные заголовки с засечками, спокойный шрифт для основного текста. Шрифты локальные и с разрешённой лицензией. Избегать агрессивного неона, дешёвого клипарта, перегруженного «магического» декора и ощущения финансового dashboard.

Центр композиции: крупная точная SVG-карта с несколькими кольцами, аккуратными подписями, гармоничной цветовой системой аспектов и подсказками. Координаты и положения рассчитываются математически, не рисуются AI. Разнести близкие подписи алгоритмом предотвращения пересечений, соединить их с фактическими положениями тонкими линиями. Визуальное смещение подписи не должно менять положение объекта в данных.

На desktop карта занимает главную часть первого экрана; рядом спокойная карточка ключевых положений. На mobile карта помещается по ширине, поддерживает увеличение и возврат масштаба; полноценные таблицы и текстовые альтернативы доступны ниже. Не переносить desktop-макет в телефон простым уменьшением.

### Обязательные анимации

1. Медленное мерцание небольшого числа звёзд и почти незаметное движение туманности на фоне.
2. Однократное плавное появление колец и линий карты за 0,8–1,5 секунды при первом открытии.
3. Мягкое свечение выбранной планеты и плавное выделение её аспектов.
4. Небольшой переход между карточками пояснений.

Не вращать рассчитанную карту непрерывно: её положение должно оставаться понятным. Учитывать prefers-reduced-motion, иметь настройку отключения декоративной анимации, останавливать фон во вкладке вне фокуса, не допускать мигания и тяжёлых эффектов. Не задерживать показ уже готовой карты ради анимации. Никакого обязательного WebGL и видеофона.

Визуальная приёмка: скриншоты 360, 390, 768 и 1440 px; отсутствие наложений и горизонтального скролла страницы; читаемые символы и контраст WCAG AA для текста; управление клавиатурой; проверка плотных скоплений планет. Результат должен выглядеть как законченный продукт, а не шаблон админки.

## 5. Расчётная модель

Движок: Swiss Ephemeris, локальные официальные файлы эфемерид для всего поддерживаемого диапазона. Путь задаётся окружением. Упаковать проверку наличия и контрольных сумм файлов. Не скачивать их при пользовательском запросе. Проверять возвращаемые флаги и ошибки: не допускать незаметной подмены выбранного источника расчёта fallback-моделью.

Настройки первой версии фиксированы и видны в описании карты:

- Тропический зодиак, геоцентрические видимые положения, стандартные поправки Swiss Ephemeris.
- Солнце, Луна, Меркурий, Венера, Марс, Юпитер, Сатурн, Уран, Нептун, Плутон и истинный северный лунный узел.
- Дома Placidus; ASC и MC при известном времени.
- Если Placidus не определён для конкретной широты/момента, явно перейти на Whole Sign, сохранить причину и показать сообщение. Не делать подмену незаметно.
- Основные аспекты между десятью планетами: соединение 0°/8°, секстиль 60°/4°, квадрат 90°/6°, тригон 120°/6°, оппозиция 180°/8°. Последнее число означает допустимый орбис в обе стороны. Узел и углы в аспекты MVP не включать.
- Нормализовать долготы в [0, 360), корректно обрабатывать переход через 0° и округление 29°59′ до следующего знака.
- Хранить скорость и признак ретроградности. Границы домов и отнесение планет к домам определить явно и протестировать.

Это продуктовые настройки первой версии, а не единственно возможный астрологический стандарт. Реализовать конфигурацией с номером версии, без разбросанных по коду констант.

### Время и география

Локальный справочник GeoNames с альтернативными названиями, координатами и IANA timezone ID. Импортируемый набор должен покрывать небольшие города, а не только столицы. Зафиксировать источник, дату, лицензию и атрибуцию. Часовые пояса: локальная IANA tzdata, версия сохранена в расчёте.

При переводе local datetime в UTC выявлять неоднозначное время осеннего перевода часов и несуществующее время весеннего перехода. Для неоднозначного времени показать два варианта со смещениями и потребовать выбор; для несуществующего потребовать исправление, без автоматического сдвига. Выбор fold хранить.

Исторические зоны до 1970 года могут быть неполными. Показывать предупреждение о проверке гражданского времени для ранних дат; администратору разрешить ручное UTC-смещение в диапазоне ±14 часов с обязательным комментарием. Хранить тип источника смещения. Не использовать современное смещение города для исторической даты.

### Тексты

Подготовленная локальная база оригинальных кратких пояснений: каждое из 12 положений Солнца, Луны и ASC, общие значения десяти планет, домов и пяти типов аспектов. Не копировать тексты ZET или чужих сайтов. Составить полный manifest текстов; если часть не готова, честно обозначить это в сдаче. Общие пояснения обозначать как общие, не выдавать их за подробную индивидуальную интерпретацию. Добавить краткую ненавязчивую пометку о символическом/развлекательном характере трактовок.

## 6. Админка и исправление данных

### Добавить клиента и создать карту

Основной экран админки: «Клиенты», заметная кнопка «Добавить клиента». В MVP у одного клиента одна натальная карта. Отдельные аккаунты клиентов не создаются. Предусмотреть Client как отдельную модель, связанную с Chart отношением один к одному.

Форма добавления:

- Имя/ФИО или понятный администратору псевдоним, обязательно, до 120 символов.
- Отображаемое имя на публичной карте, по умолчанию имя клиента; администратор может сократить его для приватности.
- Дата рождения, диапазон первой версии 1900–2100.
- Местное время рождения с точностью до минуты либо «Время неизвестно».
- Город рождения с выбором страны и региона из локального справочника.
- Необязательные внутренние заметки, видимые только администраторам.
- При неоднозначном времени выбор UTC-смещения; ручное смещение с причиной согласно разделу 5.

Поиск города начинается с двух символов, поддерживает кириллицу/латиницу, до 20 результатов и различение одноимённых мест. Требовать канонический ID, проверять координаты на сервере. Все ошибки показывать рядом с полями без потери ввода.

Кнопка «Создать клиента и карту»: проверить данные, выполнить настоящий расчёт и атомарно сохранить Client, Chart и первую ChartRevision. После успеха открыть карточку клиента с превью и действиями «Открыть карту» и «Скопировать ссылку». Показать полный URL для ручного копирования. При ошибке не создавать пустого клиента или нерабочую ссылку; сохранить заполненную форму и понятное сообщение.

Защитить от двойного нажатия и повторной отправки после сетевого таймаута с серверным idempotency key. Совпадение имени и даты рождения показывать как предупреждение о возможном дубле, но позволять явно создать отдельного человека. Не объединять записи автоматически.

Администратор самостоятельно отправляет ссылку клиенту вне сервиса. Интеграции с email/мессенджерами и автоматическая отправка не нужны.

### Список клиентов и поиск

Таблица: имя клиента, дата рождения, город, время/«неизвестно», дата создания, дата последнего изменения, активность ссылки. Действия в строке: «Открыть клиента», «Открыть карту», «Скопировать ссылку». Секретный URL не отображать постоянно во всех строках; получать только по разрешённому действию администратора. Поддержать клавиатурную навигацию и уведомление об успешном копировании.

Поиск без учёта регистра по имени/части имени, отображаемому имени, городу, точной дате рождения, внутреннему UUID и полной персональной ссылке. При поиске по ссылке извлекать token локально на сервере, не писать его в логи/query string; использовать POST с CSRF. Поиск не должен создавать внешних запросов. Фильтры по дате создания, неизвестному времени и активности; сортировка по имени/созданию/изменению; пагинация. Для частичного поиска использовать индексы PostgreSQL, например pg_trgm. Не загружать весь список в браузер.

Карточка клиента: имя, внутренние заметки, исходные данные рождения, превью карты, активная ссылка с копированием, версии и история изменений. Поля Client и текущей карты редактируются согласованно через общий сервис. Заметки и полное внутреннее имя никогда не попадают в публичный JSON/HTML.

Действия: исправить данные; проверить и пересчитать; пересчитать без изменения исходных данных; деактивировать/активировать ссылку; перевыпустить ссылку; удалить клиента и его карту с подтверждением. Часовой пояс дат интерфейса администратора задаётся отдельно от времени рождения.

### Атомарное редактирование

1. Администратор изменяет поля и указывает причину.
2. Выполняются валидация и расчёт нового результата без изменения публичной записи.
3. В короткой DB-транзакции проверить revision, записать новые входные данные, результат, номер версии и журнал изменения.
4. Если расчёт или сохранение не удались, прежние данные и карта остаются согласованными и доступными.
5. Если другой администратор уже изменил запись, сообщить о конфликте и не перезаписывать изменения.
6. Персональный URL сохраняется. Публичная страница не кешируется между версиями; при следующем открытии/обновлении показывает актуальную версию. Автообновление уже открытой вкладки не требуется.

Смена имени без изменения расчётных данных может обходиться без астрономического перерасчёта, но должна фиксироваться в истории. Ручной перерасчёт после обновления движка создаёт новую версию; обновление зависимостей не должно незаметно менять все сохранённые карты.

Деактивированный или неизвестный token возвращает одинаковую нейтральную 404-страницу. Перевыпуск ссылки делает старую недействительной, новая требует явного подтверждения администратора. Удаление удаляет карту и связанные версии с персональными данными; объяснить, что старые резервные копии исчезают по сроку хранения.

## 7. Данные

Модели:

- Client: UUID, internal_name, internal_notes, created_at, updated_at. Только для админки; пользовательских учётных данных нет.
- City: source_id, name, country, region, aliases/search index, latitude, longitude, timezone_id, dataset_version.
- Chart: client_id (OneToOne, каскадное удаление), UUID внутренний, случайный public_token, display_name, текущая revision, is_active, created_at, updated_at.
- ChartRevision: chart_id, revision, local_birth_date/time, time_unknown, city snapshot, координаты, timezone_id, fold, UTC-offset/source, resolved UTC, input JSON, result JSON, warnings, engine/library/ephemeris/tzdata/rules/text versions, calculation fingerprint, timestamp, administrator ID и reason.
- AuditEvent: actor, action, chart UUID, revision numbers, timestamp. Не дублировать полные персональные данные в свободных логах.
- Django admin users и DB-backed sessions.

Token: минимум 32 случайных байта из криптографического генератора в URL-safe кодировке, уникальный индекс. Он должен переживать рестарт, деплой, восстановление и перенос сервера. Допустимо хранить его в БД, чтобы администратор мог повторно выдать ссылку; считать БД и резервные копии конфиденциальными.

Хранить рассчитанные результаты с достаточной точностью, округлять только при отображении. Формат result JSON версионирован, содержит долготы, скорости, знаки, дома, углы, аспекты, орбисы, фактически использованную систему домов и предупреждения. Не включать секреты администратора в сериализатор публичной страницы.

## 8. Маршруты и безопасность

Публичные: GET /, GET /c/<token>/, GET /health/live, GET /health/ready. Публичных POST /charts/ и GET /places нет. Защищённые: создание клиента/карты, поиск городов и клиентов, копирование ссылки, редактирование, перерасчёт и удаление внутри /admin/. Проверять права на сервере для каждого действия, а не только скрывать кнопки. Формы используют CSRF; обработка ошибок возвращает структурированные ошибки либо HTML формы. Внешний коммерческий API не предоставляется.

Защищённые: /admin/ и операции изменения через POST. Пароли Argon2, HttpOnly/Secure/SameSite cookies, принудительный HTTPS в production, ограничение попыток входа, завершение сессии по logout и после сброса пароля. Никаких дефолтных паролей. Публичное создание запрещено; анонимный запрос создания получает 403/404 или перенаправление на вход без изменения данных. Для административных расчётов предусмотреть настраиваемый лимит от случайной перегрузки, а для публичного просмотра лимит против перебора ссылок; учитывать только доверенный reverse proxy. Обеспечить общий лимитер между workers без Redis, например на PostgreSQL.

На личных страницах: Cache-Control: private, no-store; Referrer-Policy: no-referrer; X-Robots-Tag: noindex, nofollow, noarchive. Robots.txt запрещает /c/ и /admin/, но не считается механизмом защиты. CSP с локальными ресурсами, защита от XSS, clickjacking и SQL injection. Никаких сторонних аналитики, CDN, шрифтов, пикселей и социальных виджетов.

Caddy и Gunicorn не должны записывать token и параметры рождения в access/error logs; редактировать путь /c/<redacted>/ либо исключить такие запросы из access log. Не писать тела форм в мониторинг. На health endpoint не раскрывать конфигурацию и версии. DEBUG=false, БД и Gunicorn не публикуются наружу. В контейнерах приложение работает непривилегированным пользователем.

## 9. Приёмочные тесты

Автоматические tests должны покрывать реальные риски:

1. Корректность UTC, неоднозначного/несуществующего времени, ручного смещения и перехода даты.
2. Контрольные астрономические примеры с фиксированными версиями и допустимой погрешностью. Сравнивать с официальным swetest и сохранёнными независимо проверенными эталонами; ZET не требуется. Сравнение с swetest проверяет интеграцию, но не является независимой проверкой самого движка.
3. Границы знаков/домов, орбисы через 0°, ретроградность, полярный fallback, отсутствие файлов эфемерид.
4. Неизвестное время скрывает дома/ASC/MC и не показывает ложную точность.
5. Исправление обновляет результат по старому URL; ошибка не меняет старую версию; параллельное редактирование вызывает конфликт.
6. Клиент не может менять карту; аноним не входит в админку; CSRF, XSS, rate limits и деактивация/ротация ссылок работают.
7. Восстановление backup на чистой БД сохраняет URL и версии; restart/redeploy сохраняют данные.
8. В браузере: вход администратора, «Добавить клиента», создание карты, поиск клиента среди других записей, копирование ссылки из списка и карточки, открытие клиентом без входа, интерактивная карта, админское исправление, мобильный вид и reduced motion. Проверить запрет анонимного создания/поиска и отсутствие внутренних заметок в публичных ответах; повторный submit не создаёт дубль; ошибка расчёта не оставляет пустого клиента. Проверить отсутствие внешних runtime-запросов и утечки token в логи.

Цель на ориентировочном сервере 2 vCPU/4 GB RAM: большинство одиночных расчётов до 2 секунд, открытие сохранённой карты до 1 секунды серверного времени при умеренной нагрузке. Провести небольшой замер и сообщить фактические показатели, не обещать нагрузку без измерения. Поиск по локальным городам индексирован.

## 12. Развёртывание на обычном VPS

Это инструкция для готового репозитория, который Codex должен создать по разделу 10. Сейчас команды прикладного проекта являются контрактом реализации, а не утверждением, что приложение уже написано и испытано.

### 12.1. Подготовка

Выбрать VPS с Ubuntu 24.04 LTS, ориентир 2 vCPU, 4 GB RAM, 30–50 GB SSD, постоянный IPv4, доступ по SSH-ключу. Это стартовый ресурсный ориентир, не гарантия пропускной способности. Провайдер должен предоставлять постоянный диск и понятное восстановление; платный VPS предпочтителен для обслуживания реальных клиентов.

Приобрести/использовать собственный домен и направить A-запись на IP. AAAA публиковать только при настроенном IPv6. Стабильный домен позволяет перенести сервер, сохранив ссылки. Бесплатность сервера не означает бесплатность домена.

Установить системные обновления и Docker Engine с Compose plugin по официальной инструкции Ubuntu: https://docs.docker.com/engine/install/ubuntu/. Проверить:

```bash
docker version
docker compose version
```

Использовать root либо отдельного пользователя с настроенными правами Docker, понимая, что членство в docker group даёт высокие привилегии. SSH только по ключу, административный доступ по 22 ограничить своим IP, публично открыть 80/443. У провайдера и ОС должны совпадать правила доступа. Docker может обходить некоторые правила UFW для опубликованных портов, поэтому наружу публиковать только Caddy 80/443; не публиковать PostgreSQL/приложение.

### 12.2. Установка проекта

Получить готовый репозиторий или архив в /opt/natal-chart. Команда git clone зависит от URL будущего репозитория. Все следующие команды запускать из этого каталога.

```bash
cp .env.example .env
chmod 600 .env
```

В редакторе задать домен, сильный пароль БД и уникальный DJANGO_SECRET_KEY, корректные ALLOWED_HOSTS и CSRF_TRUSTED_ORIGINS с https://. Секрет можно получить локально командой `python3 -c 'import secrets; print(secrets.token_urlsafe(64))'`; не публиковать его. Внести режим лицензии. Не коммитить .env.

Compose должен содержать db healthcheck, зависимость web от готовой БД, persistent volumes postgres_data/caddy_data/caddy_config и read-only volume с эфемеридами. Статика собирается в image. Caddy маршрутизирует динамические запросы в web:8000. Количество workers настраивается под память, потоки не используются.

```bash
docker compose build
docker compose up -d db
docker compose run --rm web python manage.py migrate --noinput
docker compose run --rm web python manage.py import_places --manifest /app/data-manifests/places.json
docker compose run --rm web python manage.py verify_ephemeris
docker compose run --rm web python manage.py createsuperuser
docker compose run --rm web python manage.py check --deploy
docker compose up -d
docker compose ps
```

Географические данные и эфемериды нужно получить предусмотренным в репозитории установщиком до импорта/проверки; точную команду Codex обязан включить в README. При отсутствии файлов остановить установку с объяснением. Для Caddy должен быть доступен домен и порты 80/443: он получает и продлевает сертификат автоматически. Не игнорировать предупреждения `check --deploy`, кроме документированно неприменимых за reverse proxy.

### 12.3. Проверка перед запуском

Открыть https://DOMAIN/admin/, войти, нажать «Добавить клиента», создать тестовую карту, найти клиента в списке и скопировать URL. Открыть URL в приватном окне без входа. В админке изменить время, убедиться в изменении карты по старому адресу. Перезапустить контейнеры и повторить проверку. Проверить HTTPS, robots/noindex, отсутствие открытого DB-порта, чистоту логов, работу лимитов и расчёта на исторической дате. Удалить тестовые персональные записи.

### 12.4. Резервное копирование

Реализовать ops/backup.sh: согласованный pg_dump в custom format, manifest версий и checksum, необходимые данные восстановления и конфигурация без утечки секретов в stdout. Эфемериды и справочники можно восстанавливать по manifest, если гарантирована их доступность; иначе включать в отдельный зашифрованный data bundle. Секреты и recovery instructions хранить отдельно и защищённо.

Хранить минимум 7 ежедневных и 4 еженедельных копии. Локальные копии на том же диске не защищают от потери сервера. Минимальный вариант без API: регулярно скачивать зашифрованные backup-файлы на свой компьютер через scp/SFTP. Для автоматического offsite backup можно использовать второй подконтрольный SSH-хост, если он есть. Не включать в ТЗ обязательную платную backup-службу.

Codex должен создать systemd service/timer ежедневного backup, блокировку параллельных запусков, проверку exit code, ограничение хранения и README установки timer. Рекомендуемая цель: RPO 24 часа при ежедневном offsite-копировании; RTO до 4 часов только после измеренной учебной процедуры. Без offsite-копии RPO при потере диска не гарантируется.

Восстановление: остановить web, сохранить текущую БД отдельной копией, восстановить выбранную копию в пустую БД через ops/restore.sh, проверить миграции/версии, запустить web, открыть контрольную личную ссылку. Restore требует явного флага подтверждения разрушительной операции и не должен стирать данные молча. Проверить это в отдельном тестовом окружении до работы с реальными клиентами.

### 12.5. Обновления и перенос

До обновления сделать и скачать backup; зафиксировать текущий release/image tag. Получить новый release, собрать образ, проверить миграции и тесты, применить миграции и запустить контейнеры. При необходимости короткого maintenance window показать понятную страницу. Не использовать `docker compose down -v`: это удаляет тома.

Для отката приложения использовать прежний image, только если схема БД совместима. В противном случае восстановить backup согласованно с предыдущим release, учитывая потерю новых записей после backup. Не обещать простой rollback после любой миграции.

Перенос: поднять тот же release на новом сервере, восстановить БД вместе с tokens и конфигурацией, проверить через временный hosts override, приостановить записи на старом, перенести финальный backup, сменить DNS, включить новый сервер. Во время DNS-перехода не допускать записей одновременно в две независимые БД. Сохранение домена и token сохраняет пользовательские URL.

## 13. Отдельно: бесплатный сервер Oracle Cloud Always Free

### Почему этот вариант

Рекомендация для бесплатного старта: полноценная VM Oracle Cloud Always Free. На ней можно держать приложение, PostgreSQL и постоянный диск, без внешних API и временной БД. Это инфраструктура крупного провайдера, но бесплатный тариф не означает гарантированную доступность и сохранность VM навсегда.

По документации на 05.11.2026: A1 Flex предоставляет суммарно 1500 OCPU-часов и 9000 GB-часов памяти в месяц, что документация описывает как 2 OCPU и 12 GB RAM; общий Always Free block storage 200 GB. Лимиты общие на tenancy, не на каждую машину. Консоль аккаунта и актуальные условия имеют приоритет. Не ориентироваться на старые статьи с другими лимитами.

Oracle предупреждает о нехватке доступных ресурсов в регионе и праве изъятия простаивающих Always Free VM. Поэтому этот вариант подходит для пилота с независимыми резервными копиями. Для обещания клиентам стабильной многолетней доступности рекомендован платный VPS. Не создавать искусственную нагрузку для обхода правил изъятия.

### 13.1. Регистрация и выбор ресурсов

1. Зарегистрировать Oracle Cloud Free Tier: https://www.oracle.com/cloud/free/. Процесс может требовать банковскую карту для проверки; регистрация и доступная ёмкость не гарантируются.
2. Выбрать домашний регион осознанно, предпочтительно в ЕС. Always Free ресурсы создаются в home region; доступность A1 проверить до окончательного плана.
3. Создать compartment natal-chart. Оставить Free account для нулевых расходов, не переходить на Pay As You Go автоматически ради доступности ресурсов. Если переход выбран владельцем, настроить quotas и бюджетные уведомления; бюджетное уведомление само по себе не останавливает расходы.
4. Создать VM.Standard.A1.Flex с пометкой Always Free Eligible, Ubuntu LTS arm64, например 1 OCPU/6 GB RAM и boot volume около 50 GB, проверяя итоговую оценку стоимости и общие лимиты аккаунта. Если Ubuntu 24.04 для выбранной shape недоступна, взять поддерживаемую доступную Ubuntu LTS и сверить установку Docker.
5. Не выбирать пробные платные ресурсы, рассчитывая на trial credits: они не являются долгосрочным бесплатным тарифом. При out of host capacity попробовать другой availability domain в том же home region или позже; не подменять shape платной без решения владельца.

### 13.2. Сеть и доступ

Создать VCN с публичной подсетью, internet gateway и маршрутом 0.0.0.0/0 к gateway, если мастер не сделал это автоматически. Назначить публичный IPv4 и убедиться в условиях его тарификации в консоли. В Security List/NSG разрешить TCP 80/443 всем и 22 только своему IP. На ОС проверить firewall; не очищать системные правила целиком. IPv6 включать только с полноценной настройкой.

Подключиться по SSH-ключу как ubuntu. Ключ хранить локально; приватный ключ не загружать в репозиторий. Направить домен на публичный IP. При изменении IP обновить DNS. Для постоянных клиентских URL использовать собственный стабильный домен; он может требовать отдельной оплаты.

### 13.3. Установка

Установить Docker и Compose по официальной инструкции для Ubuntu arm64. Затем выполнить раздел 12.2 без изменений. На A1 образ должен действительно собраться для arm64, включая обвязку Swiss Ephemeris. Не применять принудительное amd64 emulation как production-решение. Проверить расчётные эталоны на этой архитектуре.

Оставить PostgreSQL в локальном persistent volume. Не использовать временный диск контейнера для БД. Выделенных managed database и load balancer не требуется. Хранить зашифрованные backups вне VM, например на своём компьютере через SFTP. Раз в месяц выполнить восстановление в тестовую БД, не перезаписывая production.

### 13.4. Работа после пробного периода и потеря VM

Проверить, что все используемые ресурсы остаются Always Free Eligible после окончания trial. Следить за условиями, лимитами и уведомлениями аккаунта. Не обещать, что VM никогда не будет остановлена или изъята.

Если машина недоступна: проверить консоль и уведомления; не удалять volumes без проверки; создать доступную VM либо платный VPS, установить тот же release, восстановить offsite backup, направить прежний домен на новый сервер. Наличие backup, tokens и прежнего домена позволяет восстановить ссылки, но не устраняет простой.

### Почему не Render Free для постоянных карт

На дату проверки Render Free усыпляет web service после 15 минут бездействия, не предоставляет persistent disk бесплатному сервису, а бесплатная PostgreSQL истекает через 30 дней. Такой вариант неудобен для автономного сервиса с долгоживущими картами и локальной БД. Он не выбран в этой инструкции.

## 14. Итоговый критерий готовности

Проект готов, когда администратор добавляет клиента и создаёт настоящую карту без внешних API, находит его среди записей, копирует ссылку и вручную отправляет её клиенту; клиент открывает только готовую карту без входа. Администратор корректирует данные и получает обновлённую карту по прежнему URL, а после рестарта и восстановления резервной копии этот же URL продолжает работать. Визуальное оформление проходит проверку на телефоне и desktop; анимации красивы, спокойны и отключаемы. Codex предоставляет фактические результаты тестов и честно отмечает ограничения исторического времени и бесплатного хостинга.
